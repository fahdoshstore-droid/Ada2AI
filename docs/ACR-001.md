## B1: `name_ar` Naming Convention — RESOLVED

### Evidence

**Codebase uses `name_ar` in 30+ locations:**

| Layer | Files | Pattern |
|---|---|---|
| `api/` | `players.ts:37,48,50`, `academies.ts:37,48,50`, `scouts.ts:37,48,50`, `players/route.ts:39` | `.insert({ name, name_ar, ... })`, `.or('name.ilike...,name_ar.ilike...')` |
| `server/` | `apiPlayers.ts:24,75,80`, `apiScouts.ts:23,74,79`, `apiAcademies.ts:23,74,79`, `_core/rag/intents.ts:57,83,110,137,163,167` | Same patterns |
| `client/` | `Players.tsx:13,58`, `Scouts.tsx:14,79,261`, `Academies.tsx:12,71,301`, `ScoutDashboard.tsx:75,368,648`, `TrainingHub.tsx:230,232`, `useScoutPlayers.ts:21,125` | `p.name_ar`, `{lang === 'ar' && p.name_ar ? p.name_ar : p.name}` |

**Architecture mandates (Section 4, Naming Convention):**
> Arabic text: bare name. `name` = Arabic, `name_en` = English. No `_ar` suffix.

**Production database reality:**
- `players.name` already contains Arabic: `"لاعب واحد"`, `"محمد الكناري"`
- `players.name_ar` does NOT exist in production
- `players.name_en` exists and is `null`

### Decision: ARCHITECTURE WINS

**Rationale:**
1. The production database already stores Arabic in `name` — the architecture matches reality
2. The code is querying a column (`name_ar`) that doesn't exist in production
3. Arabic-first naming is correct for a Saudi platform
4. The `_ar`/`_en` suffix pattern is inconsistent with the rest of the schema

**Migration path for code:**
- `name` → stays as `name` (Arabic) — NO CHANGE to column
- `name_ar` → becomes `name` — REMOVE all `name_ar` references
- `name_en` → stays as `name_en` (English) — NO CHANGE
- Search queries: `name.ilike... OR name_ar.ilike...` → `name.ilike... OR name_en.ilike...`
- Client display: `p.name_ar || p.name` → `p.name` (always Arabic)
- Client bilingual: `lang === 'ar' && p.name_ar ? p.name_ar : p.name` → `p.name` (always Arabic, use `p.name_en` for English)

**Affected files (30+):** All API handlers, server routes, RAG intents, client pages, client hooks. Implementation will handle this systematically.

## B2: `players.region` Missing Column — RESOLVED

### Evidence

**Codebase uses `players.region` in 12+ locations:**

| File | Line | Usage |
|---|---|---|
| `api/players.ts` | 34-35 | `.eq("region", region)` filter |
| `api/players.ts` | 48,50 | `.insert({ ..., region, ... })` |
| `api/players/route.ts` | 39 | `.select('..., region, ...')` |
| `api/players/route.ts` | 68,76 | `.insert({ ..., region, ... })` |
| `server/apiPlayers.ts` | 20 | `.eq('region', ...)` filter |
| `server/apiPlayers.ts` | 80 | `.insert({ ..., region, ... })` |
| `server/_core/rag/intents.ts` | 54 | `.eq("region", params.region)` |
| `client/src/hooks/useScoutPlayers.ts` | 136 | `region: p.profile?.region \|\| p.region \|\| ''` |

**Architecture schema (Section 3.2):** `players` has 43 columns. `region` is NOT among them.

**Architecture intent:** Region lives on `profiles.region`, accessed via join `players.profile_id → profiles.region`.

### Decision: ARCHITECTURE WINS — ADD `region` TO `players`

**Rationale:**
1. The codebase universally treats `players.region` as a first-class filterable column
2. Every directory page filters by region: Players, Academies, Scouts
3. Forcing a join to `profiles` for every region filter adds unnecessary complexity
4. `region` is a display attribute, not identity data — denormalizing it on `players` is justified
5. This matches the pattern already used for `academy_name` (denormalized for display)

**Architecture Update Required:**
- Add `region` column to `players` schema (Section 3.2)
- Type: `text`, nullable, no default
- Justification: "Denormalized — displayed on every player card and used as primary filter. Source of truth is `profiles.region`, copied on player creation."
- Add index: `idx_players_region` on `(region)` — already covered by `idx_players_sport_active` composite

**This is the ONLY schema change to the architecture.** All other blockers are code-side naming fixes.

## B7: `career_history` Dead Table — RESOLVED

### Evidence

| File | Line | Usage |
|---|---|---|
| `server/apiAthleteCareer.ts` | 94 | `.from('career_history')` |

**Architecture (Section 11, Dead Architecture):**
> `career_history` — Mock data only, no real code writes to it. Replaced by aggregation from `point_transactions` + `evaluations` + `analyses`.

### Decision: ARCHITECTURE WINS — REMOVE ENDPOINT

**Rationale:**
1. `career_history` is declared dead architecture
2. The endpoint `GET /api/athletes/:id/career` already has a mock data fallback
3. Career data should be computed as an aggregation, not stored in a separate table
4. This is a Phase 2 concern — the endpoint can return aggregated data from `point_transactions` + `evaluations` + `analyses`

**Action:** The `server/apiAthleteCareer.ts` endpoint will be rewritten in Phase 2 to aggregate from live tables instead of querying `career_history`. For Pilot, the endpoint is not in scope.
