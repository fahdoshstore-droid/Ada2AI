# Ada2AI — Incident Recovery

Common production incidents and their fixes. For any incident, check Vercel deployment logs first: `vercel logs --prod`.

---

## PGRST002 — Schema Cache Error

**Symptoms**: API returns 500 errors with `PGRST002` or "schema cache" messages. PostgREST cannot reload the schema.

**Fix**:

1. Go to Supabase Dashboard → Database → Replication
2. Or run via SQL Editor:

```sql
-- Terminate stale PostgREST connections
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE usename = 'authenticator' AND query LIKE '%pgrst%';

-- Reload the schema cache
NOTIFY pgrst, 'reload schema';
```

3. If persistent, restart the Supabase API service from the Dashboard → Settings → API → Restart.

**Prevention**: Avoid making multiple rapid schema changes; let the cache reload between migrations.

## Auth Session Lost

**Symptoms**: User sees the login page despite being previously signed in. API calls return 401.

**Root cause**: Supabase session stored in `localStorage` can be cleared by browser settings, extensions, or token expiry without refresh.

**Fix**:

1. Clear stale tokens in browser DevTools → Application → Local Storage → delete `supabase.auth.token` entries
2. Call `supabase.auth.signOut()` to clean up, then sign in again
3. If persisting: check that `SUPABASE_URL` and `SUPABASE_ANON_KEY` match between client and server — mismatched keys cause token validation failures

**Prevention**: The AuthContext uses `onAuthStateChange` to auto-refresh tokens. Verify the Supabase client is initialized with `persistSession: true` (default).

## API 401 — Unauthorized Errors

**Symptoms**: All protected API endpoints return `401 Unauthorized`.

**Checklist**:

1. **Vercel env vars**: Verify `SUPABASE_URL` and `SUPABASE_ANON_KEY` are set in Vercel Dashboard → Settings → Environment Variables
2. **Client token passthrough**: The React app must send `Authorization: Bearer <access_token>` in API requests. Check that `session.access_token` is being included in fetch headers.
3. **Key mismatch**: Client and server must use the same Supabase project URL and anon key. Compare `VITE_SUPABASE_URL` (client) with `SUPABASE_URL` (server).
4. **Token expiry**: Supabase JWTs expire after 1 hour by default. The client SDK auto-refreshes, but if the refresh fails, the token becomes invalid.

**Quick test**:
```bash
curl -H "Authorization: Bearer <token>" https://your-app.vercel.app/api/players
```

## Build Failures

**Symptoms**: `vercel build` or `npx vite build` fails with TypeScript or bundler errors.

**Steps**:

1. Run `npx tsc --noEmit` locally to find type errors before deploying
2. Check that all imports resolve — path aliases like `@/` must match `vite.config.ts` and `tsconfig.json`
3. Verify `pnpm install` completes without errors
4. If using Vercel's build system, ensure `vercel.json` points to the correct `outputDirectory`

**Common issues**:
- Missing `VITE_` env vars at build time → runtime crashes, not build failures
- Circular imports → Vite may hang or throw unclear errors; use `npx madge --circular client/src/`

## RLS Blocking Queries

**Symptoms**: API returns empty arrays for authenticated users, or INSERT/UPDATE returns 403-like errors (Supabase returns empty results, not explicit 403).

**Debug steps**:

1. **Check `auth.uid()`**: In Supabase SQL Editor, run:
   ```sql
   SELECT auth.uid();
   -- With a real token:
   SELECT auth.uid() FROM (SELECT set_config('request.jwt.claims', '{"sub":"<user-uuid>"}', true)) t;
   ```

2. **Verify the RLS policy**: Check that the policy matches the table's ownership column. For `profiles`, the policy uses `auth.uid() = id`. For `players/academies/scouts`, it uses `auth.uid() = user_id`.

3. **service_role bypass**: If server-side code needs to bypass RLS, use the `service_role` key instead of `anon_key`:
   ```ts
   createClient(SUPABASE_URL, SERVICE_ROLE_KEY) // bypasses RLS
   ```
   **⚠️ Only use service_role on the server — never expose this key to the client.**

4. **Common mistake**: The `id` column in `profiles` is a UUID generated by `uuid_generate_v4()`, NOT the same as `auth.uid()`. The `user_id` column is the one that references `auth.users(id)`. RLS policies on `profiles` check `auth.uid() = id` because `profiles.id` is set to `auth.users.id` via the `handle_new_user` trigger.

## Rate Limiting (429)

**Symptoms**: API returns 429 Too Many Requests.

The server-side rate limiter (`server/_core/auth.ts`) allows **20 requests per minute per user** for Claude API-involved endpoints.

**Fix**: This is expected behavior. The client should implement retry with exponential backoff. Check `Retry-After` header for the wait time in seconds.
